# Uplift OSS Launch Hardening PRD

## Problem Statement

Uplift has an MVP implementation and an OSS-facing README/site, but it should not be published to npm as-is. Passing unit tests proves the current code compiles and a few core paths work, but it does not prove that real developers can install Uplift, copy the docs, run an example application, upload files end-to-end, understand the tradeoffs against existing OSS/hosted upload tools, or trust the library's package and documentation quality.

Before npm publication, Uplift needs a launch-hardening pass that turns it from a promising library into a credible OSS project: a real dogfood example, stronger tests, verified documentation snippets, bundle-size reporting, a modern dark-first documentation site, an UploadThing adapter, and honest positioning against UploadThing, Uppy, FilePond, and direct storage SDK approaches.

## Solution

Prepare Uplift for a cautious `0.1.0` OSS release by adding an end-to-end example application, stronger verification tooling, richer docs, and launch-positioning material.

The release should be blocked until a real example app demonstrates the core flows:

- Single avatar upload.
- Multi-file gallery upload.
- Authenticated route.
- Public route.
- React hook upload state and progress.
- Local storage by default.
- S3/R2 configuration documented through environment variables.

The documentation site should become a dark-theme-first developer reference with a light-mode toggle, better visual hierarchy, installation and quickstart paths, a comparison section, bundle-size information, and links into real examples. README badges should use reliable npm/GitHub stats, while bundle size should be generated by project tooling rather than depending on a third-party badge that may break for unpublished packages.

The implementation should add an UploadThing adapter as a storage/provider integration, not as a core dependency. UploadThing support is part of the pre-`0.1.0` launch bar, not a follow-up. Uplift should also ship with a strong OSS identity: a polished logo and Open Graph image set for the README, docs site, package pages, and social previews. Uplift's positioning should be honest: it is not universally "better" than UploadThing, Uppy, or FilePond; it is better suited for developers who want a small, self-hostable, TypeScript-first upload contract while keeping storage and database side effects inside their own application.

## User Stories

1. As a developer evaluating Uplift, I want to run a real example app, so that I can see uploads work before trusting the library.
2. As a developer evaluating Uplift, I want a local-storage example that works without cloud credentials, so that I can try Uplift quickly.
3. As a developer using S3, I want documented environment variables and configuration, so that I can adapt the example to my bucket.
4. As a developer using R2, I want documented endpoint/account configuration, so that I can adapt the S3-compatible flow to Cloudflare R2.
5. As a frontend developer, I want to see a real avatar upload UI, so that I understand the single-file route flow.
6. As a frontend developer, I want to see a real gallery upload UI, so that I understand multi-file routes.
7. As a frontend developer, I want to see React hook progress and errors in the example, so that I can model my own UI.
8. As a backend developer, I want to see an authenticated upload route in the example, so that I understand how user context flows into key and done handlers.
9. As a backend developer, I want to see a public route in the example, so that I understand `.overrideAuth()`.
10. As a developer, I want copied docs snippets to be linted or typechecked, so that examples do not drift from the package API.
11. As a maintainer, I want documentation code samples extracted or co-located with tests, so that docs break CI when the API changes.
12. As a maintainer, I want bundle-size reporting generated in CI, so that the README/site can show a reliable size signal.
13. As a developer evaluating package weight, I want bundle-size information in the docs, so that I can assess install cost.
14. As a developer who prefers dark documentation, I want the docs site to default to dark mode, so that it feels modern and comfortable.
15. As a developer who prefers light documentation, I want a light-mode toggle, so that the docs remain accessible.
16. As a developer browsing on mobile, I want the docs site to remain readable and navigable, so that I can evaluate Uplift anywhere.
17. As a developer comparing upload tools, I want a clear comparison with UploadThing, Uppy, FilePond, and direct SDK uploads, so that I can choose the right tool.
18. As a maintainer, I want the comparison to be honest and specific, so that Uplift does not overclaim.
19. As a developer who likes UploadThing, I want an UploadThing adapter path, so that I can use Uplift's route contract with UploadThing-style infrastructure where appropriate.
20. As a maintainer, I want UploadThing support isolated from core, so that core remains small and dependency-light.
21. As a developer, I want tests for malformed multipart requests, so that parser behavior is trustworthy.
22. As a developer, I want tests for storage failures, so that failed uploads do not look successful.
23. As a developer, I want tests for auth failures, so that private routes are protected.
24. As a developer, I want tests for unsafe storage keys, so that path traversal or provider-key mistakes are caught.
25. As a developer, I want tests for multi-file partial failure semantics, so that I know what happens when one file fails.
26. As a maintainer, I want framework example tests, so that documented Next/Hono/Express usage keeps working.
27. As a maintainer, I want package install smoke tests, so that published exports can be consumed from a clean app.
28. As a maintainer, I want a release checklist, so that `0.1.0` publishing is deliberate.
29. As a maintainer, I want `0.1.0` to be clearly marked as early OSS, so that users understand stability expectations.
30. As a contributor, I want a clear project structure for examples and docs, so that future docs improvements are easy to make.
31. As a developer discovering Uplift through GitHub or social links, I want a polished logo and Open Graph preview, so that the project feels credible and memorable.
32. As a maintainer, I want source assets for the logo and OG image, so that launch visuals can evolve without being recreated from scratch.

## Implementation Decisions

- Do not publish to npm until the launch-hardening checklist passes.
- Add at least one real application under an examples area.
- The first example should use local storage by default to avoid requiring cloud credentials.
- The same example should document S3/R2 environment variables or provide separate S3/R2 configuration notes.
- Use the existing Uplift package through workspace linking in examples so examples exercise the public package surface.
- Keep UploadThing support as an adapter/integration, not a core dependency.
- Add bundle-size tooling owned by the repo rather than relying on Bundlephobia badges.
- Update the README and docs site to display bundle size from generated output.
- Make the documentation site dark by default with a persistent light-mode toggle.
- Use Tailwind CDN only for the static docs site until the project chooses a full docs framework.
- Add a comparison section that positions Uplift honestly against UploadThing, Uppy, FilePond, and direct SDK uploads.
- Generate and integrate a polished logo and Open Graph image set before `0.1.0`.
- Store logo/OG assets in repo-controlled web formats and wire them into the docs metadata.
- Treat docs code samples as code: snippets should be imported from tested examples or checked by a script.
- Add stronger runtime and type coverage around the upload contract, failure modes, package exports, and examples.
- Add CI jobs or scripts for docs sample checking, bundle-size reporting, example validation, and package install smoke tests.
- Keep release as `0.1.0`, not `1.0.0`.

## Testing Decisions

- Good tests should exercise public behavior: route builders, client calls, handlers, storage adapters, example apps, and published exports.
- Avoid tests that only assert private implementation details.
- Add dogfood tests that run the example app's build/check flow.
- Add docs sample tests that fail when README/site code examples drift from Uplift's public API.
- Add runtime tests for malformed multipart requests, auth failure, validation failure, storage failure, unsafe key handling, and multi-file failure behavior.
- Add package smoke tests that pack the package, install it into a clean temporary project, and import the major subpaths.
- Add bundle-size tests or reporting scripts that produce deterministic output checked into docs or CI artifacts.
- Add UploadThing adapter tests with a mocked UploadThing-compatible API boundary.

## Out of Scope

- Publishing `1.0.0`.
- Building a hosted upload service.
- Replacing the current docs site with a full framework such as VitePress, Nextra, or Astro unless that becomes necessary later.
- Implementing every possible rich inspection feature before `0.1.0`.
- Claiming Uplift is universally better than UploadThing, Uppy, FilePond, or provider SDKs.
- Adding UploadThing as a hard core dependency.

## Further Notes

The launch message should be: Uplift is a small, self-hostable, TypeScript-first upload contract for developers who want upload routes, storage, auth, and app side effects to live in their own codebase. The most important confidence builder is not another badge; it is a real example project that a user can run and modify.
