# Review: Uplift MVP PR #12

Date: 2026-05-09  
Branch reviewed: `implement-uplift-issues`  
PR: https://github.com/Itzfeminisce/uplift/pull/12

## Summary

The project now has the rough package shape, fluent builder surface, tests, docs, and an open PR, but it is not publication-ready yet. The biggest gaps are not cosmetic: several exported adapters report success without uploading bytes, framework examples do not match real framework behavior, rich/type-specific validation methods are accepted but never enforced, and metadata inference promises do not match runtime behavior.

The current tests pass because they mostly exercise happy-path fakes. They do not yet protect the behavior that would matter to a real user after publishing.

## Review Issues

### 1. Provider storage adapters can claim success without uploading bytes

- Severity: P0 / publish blocker
- GitHub issue: https://github.com/Itzfeminisce/uplift/issues/13
- Files:
  - `packages/uplift/src/storage/s3.ts`
  - `packages/uplift/src/storage/r2.ts`
  - `packages/uplift/src/storage/bunny.ts`
  - `packages/uplift/src/storage/cloudinary.ts`
- Observation: S3 only calls an optional fake `client.send()` with no body, Bunny never calls Bunny's API, and Cloudinary only uploads when a custom test client is provided. Without a supplied fake client, all three return a successful `UploadedFile` URL for an object that was never stored.
- Loophole: App code in `.done()` can persist a `file.url` that does not exist.
- Fix direction: Implement real provider writes or clearly mark these as test stubs and remove them from publish/docs until real. S3/R2 should depend on `@aws-sdk/client-s3` or accept a real compatible client and send `PutObjectCommand` with the file body.

### 2. `.meta()` is typed into `done()` but runtime passes `undefined`

- Severity: P1
- GitHub issue: https://github.com/Itzfeminisce/uplift/issues/14
- File: `packages/uplift/src/server.ts`
- Observation: Metadata is derived inside the per-file loop, then discarded. `done()` is called later with `meta: undefined` for both single and multiple routes.
- Loophole: TypeScript tells users `meta.owner` exists, but production receives `undefined`.
- Fix direction: Preserve derived metadata through storage. For single routes, pass that file's metadata to `done()`. For multiple routes, decide whether `meta` is per-route, per-file, or an array, then update types and runtime together.

### 3. Framework handlers do not match documented framework usage

- Severity: P1
- GitHub issue: https://github.com/Itzfeminisce/uplift/issues/15
- Files:
  - `packages/uplift/src/client.ts`
  - `packages/uplift/src/next.ts`
  - `packages/uplift/src/hono.ts`
  - `packages/uplift/src/express.ts`
  - `packages/uplift/README.md`
- Observation: The client posts to `${baseUrl}/${routeName}`. The README's Next example shows a single `app/api/upload/route.ts`, which will not catch `/upload/avatar`. The Hono adapter returns `{ fetch }`, but the README passes it to `app.route()`, which expects a Hono app/router. The Express adapter constructs a Fetch `Request` from `req.body`, but real Express multipart requests arrive as Node streams, not as a `BodyInit`.
- Loophole: Users can copy the docs and get routes that never receive the client upload, or handlers that fail to parse multipart bodies.
- Fix direction: Add real integration tests per adapter. Next should document or implement a catch-all route or use a route query/body field. Hono should return a real `Hono` instance or document `app.all`. Express should bridge the raw request stream or explicitly require a compatible multipart/raw-body setup.

### 4. Advertised validators are no-ops

- Severity: P1
- GitHub issue: https://github.com/Itzfeminisce/uplift/issues/16
- Files:
  - `packages/uplift/src/builder.ts`
  - `packages/uplift/src/server.ts`
  - `packages/uplift/src/rich.ts`
- Observation: `dimensions()`, `square()`, `aspectRatio()`, `encoding()`, CSV `headers()` / `delimiter()`, rich PDF `pages()` / `encrypted()`, and rich media `duration()` only store config. `validateFile()` never checks them.
- Loophole: Routes accept invalid images, text, CSV, PDFs, audio, and videos while the API suggests enforcement.
- Fix direction: Either implement the checks behind the appropriate package boundaries or remove/mark these methods as planned. Add behavior tests with invalid files for every public validator.

### 5. The server does not use busboy despite depending on it

- Severity: P1
- GitHub issue: https://github.com/Itzfeminisce/uplift/issues/17
- Files:
  - `packages/uplift/package.json`
  - `packages/uplift/src/server.ts`
- Observation: The package depends on `busboy`, but request parsing uses `req.formData()`. This contradicts the PRD and does not provide stream-level control.
- Loophole: Large uploads may be buffered by the runtime before Uplift validation/storage logic sees them, and Express/Node stream behavior is not covered.
- Fix direction: Either implement a busboy parser for Node/server adapters or remove the dependency/claim and define the supported runtimes around Fetch `Request.formData()`.

### 6. Default auth typing is too permissive

- Severity: P2
- GitHub issue: https://github.com/Itzfeminisce/uplift/issues/18
- File: `packages/uplift/src/builder.ts`
- Observation: `UploadBuilder<TAuth = any>` and all builders return `UploadBuilder<any, ...>`. That lets unauthenticated routes type-check code like `user.id` even when no auth exists.
- Loophole: The core type-safety value prop is weakened exactly where auth/user context matters.
- Fix direction: Default auth should be `unknown`. Router-level middleware user type should propagate into route contexts, or routes should require `.auth()` to narrow `user`.

### 7. Client and React progress is not real upload progress

- Severity: P2
- GitHub issue: https://github.com/Itzfeminisce/uplift/issues/19
- Files:
  - `packages/uplift/src/client.ts`
  - `packages/uplift/src/react.ts`
- Observation: Progress jumps from `0` before `fetch()` to `100` after the response. Native Fetch does not expose upload progress this way.
- Loophole: React UIs can display precise-looking progress that does not reflect bytes uploaded.
- Fix direction: Either switch the browser client to XHR for progress support, expose coarse lifecycle state only, or document progress as coarse `0/100`.

### 8. Package publication relies on an untracked local build

- Severity: P2
- GitHub issue: https://github.com/Itzfeminisce/uplift/issues/20
- Files:
  - `packages/uplift/package.json`
  - `.gitignore`
- Observation: `files` includes `dist`, exports point at `dist`, and `dist` is gitignored. The pack check passed only because `pnpm check` had built local artifacts first. There is no `prepack`/`prepublishOnly` script to guarantee `dist` exists when publishing from a clean checkout.
- Loophole: A clean publish flow can produce a broken package or fail late depending on whether the maintainer remembered to build first.
- Fix direction: Add a package-level `prepack` or `prepublishOnly` build/check script, and add CI that runs install, check, and pack from a clean checkout.

## Observations

- `pnpm check` currently passes locally.
- `pnpm pack` currently includes `dist` artifacts after a local build.
- GitHub PR #12 is mergeable, but only GitGuardian has run; there is no GitHub Actions test/build/pack gate.
- The repo uses one package named `uplift` rather than the originally discussed one-package-per-subpath monorepo. That can be acceptable for an MVP, but it should be an explicit architecture decision because dependency isolation was part of the PRD.
- The tests are useful as smoke tests, but they are not yet adversarial enough for a file upload library. Missing tests include real provider writes, real framework mounting, invalid advertised validators, metadata in `done()`, and clean publish.

## Recommended Next Pass

1. Fix provider adapters or remove them from public docs until real.
2. Fix framework adapters against real Next/Hono/Express integration tests.
3. Make metadata runtime match metadata types.
4. Decide whether rich/type-specific validators are in scope for the first publish; implement or remove from exported API.
5. Add CI and publish safeguards.
